1. Liu/Hsu: 65,594 target vs. 74,769 available (9,175-row excess, all 4 partitions)

This is the highest-value remaining problem — it affects the corpus's best-characterized data source. Concrete things to try, in order of promise:

- Check for additional Nature supplementary files. The MOESM3 workbook (41587_2026_3261_MOESM3_ESM.xlsx) that both of us used has no read-count, coverage, or QC column at all — I just re-verified this: LibMMR and LibCV only have design fields plus 4 editing/4 indel columns, nothing else. If a coverage-based filter explains the gap, the threshold data must live somewhere else. Check the SI PDF (hsu2026_supplementary_info.pdf) for a full "Supplementary Table" index — Nature papers often deposit more MOESM files (MOESM4, MOESM5, etc.) than the one that happened to get uploaded here. A coverage/read-depth table is the single most likely explanation for a clean per-context ~12% exclusion.
- Test the pe_constants.py embedding-bound hypothesis specifically and rigorously. external/optiprime/scripts/pe/pe_constants.py defines MAX_PRE_HOM=25, MAX_POST_HOM=25, MAX_SMALL_EDIT=7, MAX_LARGE_SUB=20, MAX_LARGE_INS=50. These look like they're only for synthetic pretraining data generation, but it's worth checking whether real training rows exceeding these bounds get silently dropped too (the model's embedding table would have to be sized for them either way). I checked our own Hsu data against this: rtt_length > 25 hits 17,414 rows (too many to be the whole answer alone) and edit_length > 20 hits 2,063 rows (too few alone). Recommend they systematically test combinations (e.g. pre_hom > 25 OR post_hom > 25 OR edit_length > 20, computed from the actual split_edit-derived homology arms, not just raw PBS/RTT length) rather than testing PBS/RTT length directly — the pre/post-homology-arm lengths after alignment are what the constants actually bound, not the raw PBS/RTT columns.
- Check per-partition proportionality carefully. The excess is 2,158 / 2,148 / 2,434 / 2,435 across the 4 Liu contexts (HEK293T PE2/PE4, HeLa PE2/PE4) — notably HeLa's excess (~2,434) is consistently larger than HEK293T's (~2,150). If the true filter is a fixed design-level property (not context-dependent), the excess should scale with each context's row count, not be roughly constant across such different context sizes. Have them check whether the excess is dominated by specific Design category values that are more prevalent in the HeLa-measured subset — the previously-tried "SNPs only" filter (giving 66,594) and "exclude PAM SNP+indel" (giving 64,176) were both close but not exact; recommend a full grid search over combinations of Design category inclusion/exclusion rather than testing them one at a time, since the real filter might be a combination (e.g., exclude PAM-SNP+indel AND apply a length bound).
- Don't force a match. If none of these pan out, the honest and correct thing (which both of us already independently converged on) is to keep the full 74,769 and document the unexplained gap clearly, rather than reverse-engineering an arbitrary exclusion that merely hits the target number.
